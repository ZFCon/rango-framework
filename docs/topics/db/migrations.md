# Migrations

Migrations carry your models' table definitions from one version to the next. In Rango a migration is a Rust module
that builds a `Migration` value; `makemigrations` writes those modules for you, `migrate` applies them. This page
covers the commands, the generated source, writing migrations by hand, every operation, the `rango_migrations`
table, running migrations from code, the `POST_MIGRATE` signal and the current limits.

## The workflow

```console
$ cargo run -- makemigrations
Migrations for 'polls':
  src/polls/migrations/m0001_initial.rs
    + Create model Question
    + Create model Choice
Rebuild the project (cargo build) for the new migration to be picked up.
$ cargo run -- migrate
Operations to perform:
  Apply all migrations: polls
Running migrations:
  Applying polls.0001_initial... OK
```

1. Change your models.
2. `makemigrations` compares the models compiled into the program with the schema implied by the migrations that
   already exist, and writes one new module per changed app.
3. Rebuild. Migrations are registered when the program starts, so a migration module is only seen after it has been
   compiled in. `cargo run` does that on its own; the message above matters when you run a prebuilt binary.
4. `migrate` applies every migration that is not yet recorded as applied.

An app's `mod.rs` must declare its migrations module (`pub mod migrations;`), as the app template does. If it does
not, the generated files are never compiled and `migrate` finds nothing to apply.

## Commands

All commands are run through your project's entry point (`cargo run -- <command>`).

### `makemigrations [app_label ...]`

| Option | Meaning |
|---|---|
| `app_label ...` | Only these apps. Each must be in `installed_apps`, otherwise: `App 'x' could not be found. Is it in INSTALLED_APPS?` |
| `--dry-run` | Print what would be created; write nothing. |
| `-n`, `--name NAME` | Use `NAME` as the slug in the file name instead of the generated one. |
| `--check` | Write nothing; exit with status 1 when model changes lack a migration. |

With no changes it prints `No changes detected`. Otherwise, for every app with changes it writes
`src/<app>/migrations/m<NNNN>_<slug>.rs` (the app directory is looked up as `src/<app>` and then `./<app>`),
numbers it one above the app's latest migration and appends `pub mod m<NNNN>_<slug>;` to the app's
`migrations/mod.rs`. The module name starts with `m` because a Rust module name cannot start with a digit; the
migration's own name is `0001_initial`.

Slugs: `initial` for the first migration of an app; for a single operation a short name such as `choice` (create
model), `remove_choice_votes` or `alter_choice_votes`; otherwise `auto_<YYYYMMDD_HHMM>`.

Dependencies are filled in for you: the app's previous migration, and for every foreign key or many-to-many field that
points into another app, that app's latest migration.

### `migrate [app_label [migration_name]] [--database ALIAS] [--noinput]`

| Arguments | Effect |
|---|---|
| none | Apply everything that is not applied, for every installed app, in dependency order. |
| `polls` | Apply `polls` and the migrations it depends on. |
| `polls 0002` | Bring `polls` to the state after the migration whose name starts with `0002`. Later ones that are applied are unapplied first. |
| `polls zero` | Unapply every migration of `polls`. |

`--database` picks the alias (default `default`). Each migration runs, together with the row that records it, in
one transaction on both SQLite and PostgreSQL, so a failing migration changes nothing. At the end a line per
migration is printed (`  Applying polls.0001_initial... OK`, `  Unapplying ...`) or `  No migrations to apply.`;
`--verbosity 0` silences them. The migration name is matched by prefix, so `0001` is enough. A name that matches no
migration of the app fails with `Cannot find a migration matching '...' from app '...'.`

### `showmigrations [app_label ...] [--database ALIAS]`

```console
$ cargo run -- showmigrations
polls
 [X] 0001_initial
 [ ] 0002_choice_votes
```

### `sqlmigrate app_label migration_name [--database ALIAS] [--backwards]`

Prints the SQL a migration generates for the alias's backend, wrapped in `BEGIN;` / `COMMIT;`, with a comment per
operation. `--backwards` prints the SQL that unapplies it. Nothing is executed.

```console
$ cargo run -- sqlmigrate polls 0001
BEGIN;
--
-- Create model Question
--
CREATE TABLE "polls_question" ("id" integer NOT NULL PRIMARY KEY AUTOINCREMENT, ...);
...
COMMIT;
```

## The generated source

`makemigrations` writes the models as data, not as references to your structs, so a migration keeps meaning the same
thing after the struct changes:

```rust
//! Generated by `makemigrations` (Rango 0.1.0) on 2026-11-15 18:37.

#![allow(unused_imports)]

use rango::db::migrations::{Migration, Operation};
use rango::db::models::meta::Default_;
use rango::db::models::{Field, FieldType, Index, ModelMeta, OnDelete};
use rango::db::Value;

pub fn migration() -> Migration {
    Migration::new("todos", "0001_initial")
        .initial()
        .operation(Operation::CreateModel(
            ModelMeta::new("todos", "Todo").ordering(&["-id"])
                .field(Field::new("id", FieldType::Auto).with(|f| { f.primary_key = true; }))
                .field(Field::new("title", FieldType::Char).with(|f| { f.max_length = Some(200); }))
                .field(Field::new("notes", FieldType::Text).with(|f| { f.blank = true; }))
                .field(Field::new("done", FieldType::Boolean).with(|f| { f.default = Some(Default_::Value(Value::Bool(false))); }))
                .field(Field::new("created", FieldType::DateTime).with(|f| { f.blank = true; f.editable = false; f.auto_now_add = true; }))))
}

rango::db::register_migration!(migration);
```

`register_migration!(path)` takes a `fn() -> Migration` and registers it at link time. Edit these files freely;
they are ordinary source.

### `Migration`

| Item | Meaning |
|---|---|
| `Migration::new(app, name)` | A migration of app `app` called `name`. |
| `.initial()` | Marks the first migration of an app. |
| `.dependency(app, name)` | Must be applied first. Use the name `"__first__"` or `"__latest__"` for an app's first or latest migration. |
| `.operation(op)` | Appends an operation. Operations run in order. |
| fields `app_label`, `name`, `dependencies`, `operations`, `initial`, `replaces` | The data. `replaces` is stored but not used. |
| `key()` | `(app_label, name)`. |

A dependency on a migration that does not exist fails the load with
`Migration a.b dependencies reference nonexistent parent node ('x', 'y')`; a cycle fails with
`Circular dependency in migrations at app.name`. Migrations of one app are ordered by name, which is why the numbers
are zero-padded.

## Operations

`Operation` is an enum. Labels are `app_label.ModelName` (matched case-insensitively).

| Variant | Does | Reversible |
|---|---|---|
| `CreateModel(ModelMeta)` | `CREATE TABLE`, plus link tables for many-to-many fields, indexes and unique constraints. | yes |
| `DeleteModel { label }` | `DROP TABLE` (and its link tables). | yes (from the earlier state) |
| `RenameModel { old, new_name }` | Renames the table when it has the default name. `old` is a label, `new_name` a bare name. | yes |
| `AddField { label, field }` | `ALTER TABLE ... ADD COLUMN`, or a link table for a many-to-many field. | yes |
| `RemoveField { label, name }` | `DROP COLUMN` (or drop the link table). | yes |
| `AlterField { label, field }` | Change type, nullability or uniqueness. PostgreSQL uses `ALTER COLUMN`; SQLite rebuilds the table. | yes |
| `RenameField { label, old, new_name }` | Renames the column when its column name changes. | yes |
| `AddIndex { label, index }` | `CREATE INDEX`. | yes, if the index has a name |
| `RemoveIndex { label, name }` | `DROP INDEX`. | yes |
| `AlterUniqueTogether { label, groups }` | Adds and drops unique constraints so that they match `groups`. | yes |
| `RunSql { forward, reverse }` | Runs the statements in `forward`; `reverse` is used when unapplying. | yes |
| `RunCode { forward, reverse }` | Runs an async function inside the migration's transaction. | see below |

`Operation::describe()` gives the text shown by `makemigrations`, `showmigrations` and `sqlmigrate`.
Building a field by hand uses the same builder the generated code does (`Field::new`, `Field::char(name, len)`,
`Field::foreign_key(name, "app.Model", OnDelete::Cascade)`, `.null()`, `.unique()`, `.with(|f| ...)`; the full list is
in the [model field reference](../../ref/model-fields.md#building-fields-by-hand)).

### A hand-written migration

Create the file next to the generated ones, declare it in `migrations/mod.rs` (`pub mod m0002_backfill;`) and make it
depend on the previous one:

```rust
use std::future::Future;
use std::pin::Pin;
use std::sync::Arc;

use rango::db::migrations::{Migration, Operation};
use rango::db::models::{Field, FieldType};
use rango::db::Executor;
use rango::Result;

fn clear_negative_votes(db: &dyn Executor) -> Pin<Box<dyn Future<Output = Result<()>> + Send + '_>> {
    Box::pin(async move {
        db.execute("UPDATE polls_choice SET votes = 0 WHERE votes < 0", &[]).await?;
        Ok(())
    })
}

pub fn migration() -> Migration {
    Migration::new("polls", "0002_backfill")
        .dependency("polls", "0001_initial")
        .operation(Operation::AddField {
            label: "polls.Choice".into(),
            field: Field::new("note", FieldType::Text).with(|f| f.null = true),
        })
        .operation(Operation::RunSql {
            forward: vec!["CREATE INDEX polls_choice_votes_idx ON polls_choice (votes)".into()],
            reverse: vec!["DROP INDEX polls_choice_votes_idx".into()],
        })
        .operation(Operation::RunCode { forward: Arc::new(clear_negative_votes), reverse: None })
}

rango::db::register_migration!(migration);
```

Guidelines:

- Write data migrations in SQL (`db.execute`) rather than through your model structs. The structs describe the schema
  of today; a migration has to work against the schema as of its place in the history.
- `RunSql` statements are sent as they are, one batch each, on every backend. If SQLite and PostgreSQL need different
  SQL, branch in a `RunCode` function with `db.vendor()`.
- A `RunCode` function receives the migration's transaction as `&dyn Executor`. It runs after the SQL of its own
  operation and before the next operation.
- `makemigrations` cannot write `RunCode` (it is a function) and writes an empty `RunSql` in its place if you ever
  feed it one; keep those operations in files you maintain yourself.

### What the detector recognises

`makemigrations` finds, per app:

- new models (created in dependency order; a cycle of foreign keys is broken by adding the fields afterwards);
- deleted models;
- added, removed and changed fields (any difference between the old and new field definition, including
  `verbose_name` or `help_text`, produces an `AlterField`);
- added and removed indexes and changed `unique_together` groups.

It does not notice a renamed field or model: a rename shows up as a removal plus an addition, which drops the data.
Write `RenameField` / `RenameModel` yourself and delete the generated pair. It also does not look at `db_table`,
`ordering`, `verbose_name` or the other options that do not change the schema. A model with `managed = false` is
skipped entirely. Adding a non-null field to an existing model without a `default` fails, because the existing rows
would have no value:

```text
You are trying to add a non-nullable field 'rating' to choice without a default; we can't do that (the database needs
something to populate existing rows). Give the field a default (#[field(default = ...)]) or make it nullable.
```

## What gets recorded: `rango_migrations`

`migrate` and `showmigrations` create the table on first use (`CREATE TABLE IF NOT EXISTS`):

| Column | SQLite | PostgreSQL |
|---|---|---|
| `id` | `integer PRIMARY KEY AUTOINCREMENT` | `bigint ... GENERATED BY DEFAULT AS IDENTITY` |
| `app` | `varchar(255)` | `varchar(255)` |
| `name` | `varchar(255)` | `varchar(255)` |
| `applied` | `datetime` | `timestamp with time zone` |

A row is inserted when a migration is applied and deleted when it is unapplied. The table is not a model, so it is
not part of any migration and `flush` leaves it alone.

## Running migrations from code

`rango::db::migrations` exposes what the commands use. This is how the framework's own tests build their schema:

```rust
use rango::db::migrations::{MigrationLoader, Target, executor};
use rango::db::Db;

let db = Db::default_db();
let labels: Vec<String> = ["contenttypes", "auth", "sessions", "polls"].map(String::from).to_vec();

let loader = MigrationLoader::load(Some(&labels))?;               // Option<&[String]>: only these apps
let lines = executor::migrate(&db, &loader, &Target::All).await?; // Vec<String>, one per migration
assert_eq!(lines.last().map(String::as_str), Some("  Applying polls.0001_initial... OK"));
```

| Item | Meaning |
|---|---|
| `MigrationLoader::load(Option<&[String]>)` | Collects every registered migration (optionally only of the listed apps) and orders them by dependency. |
| `MigrationLoader::from_migrations(Vec<Migration>)` | A loader over migrations you built yourself, for tests. |
| `loader.migrations` / `loader.order` | The map from `(app, name)` to migration, and the dependency order. |
| `loader.leaf(app)` | The latest migration of an app. |
| `loader.with_dependencies(&key)` | A migration and all its ancestors. |
| `loader.full_state()` / `state_for(&keys)` | The `ProjectState` after applying migrations. |
| `executor::migrate(&Db, &MigrationLoader, &Target)` | Apply or unapply. Takes a `Db`, because it needs to open transactions. |
| `Target::All` | Everything. |
| `Target::App(String)` | An app and its dependencies. |
| `Target::Migration(String, String)` | `(app, name prefix)`; the name `"zero"` unapplies the whole app. |
| `executor::applied(&db)` | `HashSet<(String, String)>` of applied migrations. |
| `executor::ensure_recorder(&db)` | Creates `rango_migrations` if it does not exist. |
| `executor::migration_sql(&loader, &key, vendor, backwards)` | The SQL a migration would run. |

`migrate` on an in-memory SQLite database works because it runs each migration on the pool's single connection. The
loader rebuilds migrations from their registered functions each time you call `load`.

## Migrations of bundled apps

The contrib apps (`auth`, `contenttypes`, `sessions`, `sites`, ...) ship no migration files. Each registers an
`0001_initial` that is computed when the program starts from the app's current model definitions:

```rust
rango::db::register_initial_migration!("sessions", [("contenttypes", "0001_initial")]);
```

The arguments are the app label and the list of `(app, migration)` dependencies. You can use the macro for your own
reusable crates that define models but keep no migration files. Because that migration is always derived from the
current models, it never produces a later migration: if a model of such an app changes in a new version, you need a
migration of your own. `rango::db::migrations::initial_for_app(label, &[deps])` builds the same `Migration` value.

## The `POST_MIGRATE` signal

After every `migrate` run, `POST_MIGRATE` is sent once for each app known to the loader (also when nothing was
applied), with the app label as sender and a `MigrateEvent { app_label, using }` payload. The bundled apps use it to
create content types, permissions and the default site. `flush --noinput` sends it again after emptying the tables.

```rust
use rango::db::migrations::executor::POST_MIGRATE;
use rango::db::Db;
use rango::dispatch::ConnectOptions;

// Connect once, for example from the app's `ready` hook.
POST_MIGRATE.connect(
    |d| async move {
        let db = Db::using(&d.args.using);
        // seed rows for d.args.app_label with `db` ...
        let _ = db;
    },
    ConnectOptions::sender("polls").uid("polls.seed_after_migrate"),
);
```

`ConnectOptions::sender("polls")` limits the receiver to that app; `.uid(...)` makes connecting twice register it
once. `PRE_MIGRATE` exists in the same module but is not sent by `migrate`.

## Limits

- No `squashmigrations`, no `migrate --fake`, `--plan` or `--run-syncdb`.
- Renames are not detected; `db_table`, `ordering` and other non-schema options are not diffed.
- Unapplying runs the reverse of the schema operations and of `RunSql`, but does **not** run the `reverse` of a
  `RunCode` operation, and an operation that has no reverse (a `RunCode` with `reverse: None`) is skipped without an
  error.
- Unapplying a migration does not look for other apps that depend on it.
- On SQLite, `AlterField` rebuilds the table (create new table, copy rows, drop, rename). The copy keeps the data and
  the inline constraints but does not recreate secondary indexes (`db_index` columns and `unique_together`); add them
  back with a `RunSql` operation when you alter a field of a table that has them.
- Check constraints, conditional indexes and multi-column indexes cannot be declared on a model, so
  `makemigrations` never generates them; `AddIndex` works from hand-written migrations.
- Choices, validators and comments on fields are not part of the schema.
