# Internationalisation

Rango translates text with gettext message catalogs: you mark strings in Rust code and in templates, extract them
into a `.po` file per language, translate that file, and Rango picks the right catalog for each request. This page
covers marking strings, the catalog layout, the `makemessages` and `compilemessages` commands, choosing the active
language, and what is not supported yet.

Formatting of dates and numbers per locale is a separate topic: see [Localisation](l10n.md).

## Overview

```rust
use rango::utils::translation::{gettext, ngettext, npgettext, pgettext};
```

| Step | What you do |
|------|-------------|
| Mark | Call `gettext("...")` in Rust, use `{% trans "..." %}` in templates |
| Extract | `cargo run -- makemessages -l cs` writes `locale/cs/LC_MESSAGES/rango.po` |
| Translate | Fill in the `msgstr` lines of the `.po` file |
| Compile (optional) | `cargo run -- compilemessages` writes `rango.mo` next to each `rango.po` |
| Load | List the directory in the `locale_paths` setting |
| Select | Add `LocaleMiddleware`, or call `override_language` yourself |

The catalog domain is always `rango`: the files are named `rango.po` and `rango.mo`, for your project's strings as
well as for anything else.

## Settings

| Setting | Default | Meaning |
|---------|---------|---------|
| `language_code` | `"en-us"` | Language used when nothing else selects one |
| `languages` | a built-in list of about 100 `(code, name)` pairs | Languages the site accepts; read by `LocaleMiddleware` and `{% get_available_languages %}` |
| `locale_paths` | `[]` | Directories that contain `<locale>/LC_MESSAGES/rango.po` |
| `language_cookie_name` | `"rango_language"` | Cookie that `LocaleMiddleware` reads |
| `language_cookie_age`, `language_cookie_domain`, `language_cookie_path`, `language_cookie_secure`, `language_cookie_httponly`, `language_cookie_samesite` | `None`, `None`, `"/"`, `false`, `false`, `None` | Not read by the framework; use them when you set the cookie yourself (see below) |
| `use_i18n` | `true` | Defined, but nothing in the framework consults it yet; translation is always on |

A typical configuration:

```rust
use rango::conf::Settings;

pub fn settings() -> Settings {
    Settings {
        language_code: "en-us".into(),
        languages: vec![("en".into(), "English".into()), ("cs".into(), "Czech".into())],
        locale_paths: vec!["locale".into()],
        middleware: [
            "rango.middleware.common.CommonMiddleware",
            "rango.middleware.locale.LocaleMiddleware",
        ]
        .map(String::from)
        .to_vec(),
        ..Settings::default()
    }
}
```

Set `languages` explicitly. With the default list almost every language a browser asks for counts as supported,
so a request is tagged `Content-Language: de` even though you have no German catalog and the text stays in English.

Relative entries in `locale_paths` are resolved against the working directory of the process.

## Marking strings in Rust

All four functions return an owned `String` in the language that is active *at the moment of the call*.

| Function | Use |
|----------|-----|
| `gettext(message: &str) -> String` | A plain message |
| `ngettext(singular: &str, plural: &str, n: u64) -> String` | A message with a singular and a plural form |
| `pgettext(context: &str, message: &str) -> String` | A message disambiguated by a context string |
| `npgettext(context: &str, singular: &str, plural: &str, n: u64) -> String` | Context and plural together |

```rust
use rango::http::{HttpRequest, HttpResponse};
use rango::utils::translation::{gettext, ngettext, pgettext};
use rango::Result;

async fn inbox(_: HttpRequest) -> Result<HttpResponse> {
    let unread: u64 = 3;
    let title = gettext("Inbox");
    // "May" the month, not "may" the verb.
    let month = pgettext("month", "May");
    let summary = ngettext("%(n)d unread message", "%(n)d unread messages", unread)
        .replace("%(n)d", &unread.to_string());
    Ok(HttpResponse::new(format!("<h1>{title}</h1><p>{month}: {summary}</p>")))
}
```

Things to know:

- **A missing translation is not an error.** If there is no catalog for the active language, no entry for the
  message, or the entry's `msgstr` is empty, the original string is returned. For the plural functions the fallback
  is `singular` when `n == 1`, otherwise `plural`.
- **No interpolation is done for you.** The functions return the translated text with its placeholders intact.
  Use named placeholders such as `%(n)d` or `%(name)s` (the same form the template tags produce) and substitute
  them with `str::replace`. Do not build sentences by concatenating translated fragments; word order differs
  between languages.
- **Translate at the point of use.** There is no lazy string type. A translated `String` stored in a `static`, a
  `const`-like global or a struct built at start-up keeps the language that was active when it was created. Call
  `gettext` inside the view, form method or template where the text is produced.
- **Pass string literals.** `makemessages` only finds messages written as literals directly in the call
  (see [what is extracted](#what-is-extracted)).

## Marking strings in templates

Load the tag library first:

```html
{% load i18n %}
```

### `{% trans %}` / `{% translate %}`

The two names are the same tag.

```html
{% load i18n %}
<h1>{% trans "Inbox" %}</h1>
<p>{% translate "May" context "month" %}</p>

{% trans "Sign in" as sign_in %}
<a href="/login/" title="{{ sign_in }}">{{ sign_in }}</a>
```

| Argument | Effect |
|----------|--------|
| `"literal"` or a variable | The message. A variable is resolved first and its value is looked up in the catalog |
| `context "..."` | Message context (like `pgettext`) |
| `as name` | Store the result in a template variable instead of printing it |
| `noop` | Resolve but do not translate (marks the string for extraction only) |

Any other argument is a template syntax error.

A quoted literal is written to the output as it is, without HTML escaping, so do not put untrusted text in one.
A message that comes from a variable is escaped when autoescaping is on.

### `{% blocktrans %}` / `{% blocktranslate %}`

Use the block form when the message contains variables or needs a plural. Either `{% endblocktrans %}` or
`{% endblocktranslate %}` closes it.

```html
{% load i18n %}
{% blocktrans with name=user.first_name %}Hello, {{ name }}!{% endblocktrans %}

{% blocktrans count c=messages|length trimmed %}
  {{ c }} unread message
{% plural %}
  {{ c }} unread messages
{% endblocktrans %}
```

| Option | Effect |
|--------|--------|
| `with a=expr b=expr` | Bind values for use inside the block. A bare `a=expr` without `with` is accepted too |
| `count name=expr` | The number that selects the plural form; requires a `{% plural %}` section |
| `context "..."` | Message context |
| `trimmed` | Strip each line of the body, drop empty lines and join the rest with single spaces |
| `asvar name` | Store the result in a variable (marked safe) instead of printing it |

The body is turned into a message id: `{{ name }}` becomes `%(name)s` and a literal `%` becomes `%%`. The block
above therefore looks up `Hello, %(name)s!`, and that is what the translator sees:

```po
msgid "Hello, %(name)s!"
msgstr "Ahoj, %(name)s!"
```

Rules for the body, each enforced with a template syntax error:

- only text and plain `{{ variable }}` references; no other tags;
- no filters inside the block: bind the filtered value with `with` first;
- no dotted lookups such as `{{ user.name }}`: bind them with `with` first;
- `count` without `{% plural %}` is an error.

Variable values are HTML-escaped when substituted, unless they are already marked safe:

```html
{% blocktrans with name=who %}Hello, {{ name }}!{% endblocktrans %}
```

renders `Ahoj, &lt;Ann&gt;!` for `who = "<Ann>"` under the Czech catalog.

Use `trimmed` for multi-line blocks. Without it the newlines and indentation are part of the message id, and the
id changes whenever the template is re-indented.

### `{% language %}`

Renders its body in another language:

```html
{% load i18n %}
{% language "cs" %}{% trans "Hello" %}{% endlanguage %}
```

It takes exactly one argument, a literal or a variable. See the caveat under [Limits](#limits) before using it in
request handling.

### Language information tags

```html
{% load i18n %}
{% get_current_language as LANGUAGE_CODE %}
{% get_current_language_bidi as LANGUAGE_BIDI %}
{% get_available_languages as LANGUAGES %}

<html lang="{{ LANGUAGE_CODE }}"{% if LANGUAGE_BIDI %} dir="rtl"{% endif %}>
<ul>
  {% for lang in LANGUAGES %}<li>{{ lang.0 }}: {{ lang.1 }}</li>{% endfor %}
</ul>
```

| Tag | Value |
|-----|-------|
| `get_current_language` | The active language code, for example `en-us` |
| `get_current_language_bidi` | `true` for right-to-left languages (`ar`, `ckb`, `fa`, `he`, `ur`) |
| `get_available_languages` | The `languages` setting as a list of `[code, name]` pairs |

There is no context processor that adds `LANGUAGE_CODE` to every template; use the tags.

## Catalog files

### Layout

```
locale/
    cs/
        LC_MESSAGES/
            rango.po
            rango.mo        (optional, written by compilemessages)
    pt_BR/
        LC_MESSAGES/
            rango.po
```

Directory names are locale names: the language code with an underscore, the region in upper case (`pt-br` is
`pt_BR`) and a script subtag capitalised (`zh-hans` is `zh_Hans`). `rango::utils::translation::to_locale` does the
conversion.

### Where Rango looks

For the active language Rango reads, in this order:

1. every directory in `locale_paths`;
2. the `locale/` directory of every installed app whose `AppConfig` has a path
   (`AppConfig::new("blog").path("src/blog")`);
3. directories registered at run time with `add_locale_dir`.

In each directory it tries the full locale first and then the base language, so `cs-cz` reads `cs_CZ` and then
`cs`. All catalogs found are merged; when the same message appears more than once, the first one found wins.
This means a project-level catalog in `locale_paths` overrides an app's own translations.

In each `LC_MESSAGES` directory `rango.mo` is preferred. `rango.po` is read directly when there is no `.mo` (or it
is not a valid `.mo` file), so compiling is optional. If both exist, remember to recompile after editing the `.po`.

Catalogs are loaded on first use and cached for the life of the process. Restart the server after changing a
catalog, or call `reset_catalogs()`:

```rust
use rango::utils::translation::{add_locale_dir, reset_catalogs};

add_locale_dir("vendor/extra_locale"); // also clears the cache
reset_catalogs();
```

### The `.po` format

```po
msgid ""
msgstr ""
"Content-Type: text/plain; charset=UTF-8\n"
"Plural-Forms: nplurals=3; plural=(n==1 ? 0 : n>=2 && n<=4 ? 1 : 2);\n"

#: src/views.rs
msgid "Hello"
msgstr "Ahoj"

msgctxt "month"
msgid "May"
msgstr "Květen"

msgid "%(n)d file"
msgid_plural "%(n)d files"
msgstr[0] "%(n)d soubor"
msgstr[1] "%(n)d soubory"
msgstr[2] "%(n)d souborů"

msgid "A long message "
"continued on a second line"
msgstr "Dlouhá zpráva "
"pokračující na druhém řádku"
```

The parser understands `msgctxt`, `msgid`, `msgid_plural`, `msgstr`, `msgstr[N]`, continuation lines and the
escapes `\n`, `\t`, `\r`, `\"` and `\\`. Comment lines are ignored. Entries flagged `#, fuzzy` are skipped, so a
fuzzy translation is never shown.

### Plural forms

The `Plural-Forms` line of the header entry decides which `msgstr[N]` is used for a number. `nplurals` is the
number of forms and `plural` is an expression in `n` that yields the index. The expression may use integers, `n`,
parentheses, `!`, the arithmetic operators `+ - * / %`, the comparisons `== != < > <= >=`, `&&`, `||` and the
ternary `? :`.

With the Czech rule above:

```rust
use rango::utils::translation::ngettext;

let f = |n| ngettext("%(n)d file", "%(n)d files", n);
// f(1) == "%(n)d soubor"
// f(3) == "%(n)d soubory"
// f(5) == "%(n)d souborů"
// f(0) == "%(n)d souborů"
```

A catalog without a `Plural-Forms` header uses the two-form rule `n != 1`. An index beyond `nplurals - 1` is
clamped to the last form. If the selected form is empty, the untranslated singular or plural is returned.

## `makemessages`

```console
$ cargo run -- makemessages -l cs
processing locale cs
$ cargo run -- makemessages -l cs -l de --path .
```

| Option | Meaning |
|--------|---------|
| `-l`, `--locale LOCALE` | Locale to create or update. Required; repeat it for several locales |
| `--path DIR` | Directory to scan and to write `locale/` into. Default `.` |

The command scans `DIR` recursively, skipping directories named `target`, `.git`, `node_modules` and `locale`, and
writes `DIR/locale/<locale>/LC_MESSAGES/rango.po`. It does not run the system checks.

The output directory is not added to `locale_paths` for you. For the default `--path .` put `"locale"` in
`locale_paths`.

### What is extracted

From `*.rs` files: calls to `gettext(`, `ngettext(`, `pgettext(` and `npgettext(` whose message arguments are
ordinary string literals.

```rust
use rango::utils::translation::{self, gettext};

gettext("Save");                                // found
translation::pgettext("menu", "Open");          // found, with context "menu"
translation::ngettext("%(n)d row", "%(n)d rows", n); // found, with its plural

let label = "Save";
gettext(label);                                 // not found: not a literal
gettext(r"Save");                               // not found: raw string literals are not recognised
```

Function definitions named like the translation functions are ignored.

From `*.html` and `*.txt` files: `{% trans %}` and `{% translate %}` tags whose first argument is a quoted
literal, with their `context "..."` if present.

Not extracted:

- the bodies of `{% blocktrans %}` / `{% blocktranslate %}` blocks;
- `{% trans variable %}`;
- messages built at run time.

### What is written

- Entries are sorted and each one carries a `#:` comment listing the files (relative to `--path`) where it occurs.
- Translations already in the file are kept, matched by context and message id.
- The existing header is kept. A new file gets
  `Plural-Forms: nplurals=2; plural=(n != 1);`. For a language with a different rule, edit the header by hand and
  run the command again; plural entries then get `nplurals` empty `msgstr[N]` lines.
- The file is rewritten from the messages found in the sources. An entry whose message no longer occurs in the
  sources is dropped, and so is a hand-written entry. Entries flagged fuzzy are dropped too, because the parser
  skips them.

Because of the last point, messages that `makemessages` cannot find (the `blocktrans` ids, for instance) should
live in a second catalog directory that the command does not write to:

```
locale/cs/LC_MESSAGES/rango.po          # written by makemessages
locale_manual/cs/LC_MESSAGES/rango.po   # maintained by hand
```

```rust
locale_paths: vec!["locale".into(), "locale_manual".into()],
```

## `compilemessages`

```console
$ cargo run -- compilemessages
processing file rango.po in ./locale/cs/LC_MESSAGES
```

| Option | Meaning |
|--------|---------|
| `--path DIR` | Directory to search. Default `.` |

Every file named `rango.po` below `DIR` (outside `target` and `.git`) is compiled to a `rango.mo` beside it. The
`.mo` file is a standard little-endian GNU catalog and carries the header, contexts and plural forms. Fuzzy
entries are left out.

## Choosing the language

`get_language()` returns the active language. It is resolved in this order:

1. the language set with `activate` on the current thread;
2. the language of the enclosing `override_language` scope;
3. the `language_code` setting;
4. `"en-us"` when settings are not configured.

### Per request: `LocaleMiddleware`

```rust
middleware: [
    "rango.middleware.common.CommonMiddleware",
    "rango.middleware.locale.LocaleMiddleware",
]
.map(String::from)
.to_vec(),
```

For each request the middleware:

1. reads the cookie named by `language_cookie_name` (`rango_language`) and uses its value if it is a supported
   language;
2. otherwise walks the `Accept-Language` header from the highest quality value down and takes the first supported
   language (entries with `q=0` are ignored and `*` ends the search);
3. otherwise uses `language_code`.

A language is supported when it is listed in `languages`, equals `language_code`, or has a catalog directory. If
the exact code is not supported the base language is tried (`cs-CZ` matches `cs`), and after that any entry of
`languages` that starts with the base (`es` matches `es-ar`).

The view runs inside `override_language(lang, ...)`. On the way out the middleware adds `Accept-Language` to the
`Vary` header and sets `Content-Language` unless the view already set it.

```rust
use rango::test::Client;

let r = Client::new()?
    .default_header("Accept-Language", "de;q=0.9, cs-CZ;q=0.8, en;q=0.5")
    .get("/h/")
    .await?;
assert_eq!(r.text(), "Ahoj");
assert_eq!(r.header("Content-Language"), Some("cs"));
assert_eq!(r.header("Vary"), Some("Accept-Language"));

// The cookie wins over the header.
let r = Client::new()?
    .default_header("Cookie", "rango_language=en")
    .default_header("Accept-Language", "cs")
    .get("/h/")
    .await?;
assert_eq!(r.text(), "Hello");
```

The helpers the middleware uses are public in `rango::middleware::locale`:

| Function | Returns |
|----------|---------|
| `get_language_from_request(request: &HttpRequest) -> String` | The language the middleware would pick |
| `get_supported_language_variant(code: &str) -> Option<String>` | The supported language matching `code`, lower-cased |
| `parse_accept_lang_header(header: &str) -> Vec<(String, f64)>` | `(language, quality)` pairs, best first |

### Letting users pick a language

There is no built-in language-switching view. Write one that stores the choice in the language cookie:

```rust
use rango::conf::settings;
use rango::http::{CookieOptions, HttpRequest, HttpResponse};
use rango::middleware::locale::get_supported_language_variant;
use rango::shortcuts::redirect;
use rango::Result;

async fn set_language(req: HttpRequest) -> Result<HttpResponse> {
    let post = req.post().await?;
    let mut response = redirect("/")?;
    if let Some(lang) = post.get("language").and_then(get_supported_language_variant) {
        let s = settings();
        response.set_cookie(
            &s.language_cookie_name,
            &lang,
            &CookieOptions {
                max_age: s.language_cookie_age,
                path: s.language_cookie_path.clone(),
                domain: s.language_cookie_domain.clone(),
                secure: s.language_cookie_secure,
                httponly: s.language_cookie_httponly,
                samesite: s.language_cookie_samesite.clone(),
                ..CookieOptions::default()
            },
        )?;
    }
    Ok(response)
}
```

Validating the value with `get_supported_language_variant` keeps arbitrary input out of the cookie.

### In async code: `override_language`

```rust
use rango::utils::translation::{gettext, override_language};

let subject = override_language("cs", async { gettext("Hello") }).await;
assert_eq!(subject, "Ahoj");
```

The language applies to the future you pass and everything it awaits on the same task. It is task-local on
purpose: many requests run on the same threads, and a task-local value follows one request across threads without
leaking into the others. The consequence is that a task started with `tokio::spawn` inside the scope does **not**
inherit the language. Wrap the spawned future yourself:

```rust
use rango::utils::translation::{get_language, override_language};

let lang = get_language();
tokio::spawn(async move {
    override_language(&lang, send_welcome_email()).await;
});
```

This is how you send an email in the recipient's language from a background job, or render one page in several
languages.

### In synchronous code and tests: `activate` / `deactivate`

```rust
use rango::utils::translation::{activate, deactivate, gettext};

activate("cs");
assert_eq!(gettext("Hello"), "Ahoj");
deactivate();
assert_eq!(gettext("Hello"), "Hello");
```

`activate` sets the language for the current **thread** and takes precedence over `override_language`. Always pair
it with `deactivate`. Do not call it from a view on a multi-threaded runtime: the value stays with the worker
thread after your task moves on and changes the language of unrelated requests that run on that thread later.

### Other helpers

| Function | Meaning |
|----------|---------|
| `get_language() -> String` | The active language |
| `get_language_bidi() -> bool` | Whether the active language is written right to left |
| `to_locale(language: &str) -> String` | `"en-us"` to `"en_US"` |
| `available_languages() -> Vec<String>` | `language_code` plus every language that has a catalog directory |
| `Catalog::from_po(text)`, `Catalog::from_mo(bytes)`, `Catalog::to_mo(entries, header)`, `catalog.entries()` | Read and write catalogs directly |

## Limits

Not supported yet:

- **Lazy translation strings.** Call the `gettext` family when the text is produced.
- **Language prefixes in URLs** (`/cs/about/`). The language comes from the cookie or `Accept-Language` only, and
  URL patterns themselves cannot be translated.
- **A language-switching view.** Set the cookie yourself as shown above.
- **Storing the language in the session.**
- **Extraction of `{% blocktrans %}` bodies** by `makemessages`, obsolete-entry markers, line numbers in `#:`
  references, and merging of fuzzy entries.
- **Translations of Rango's own messages.** No catalogs are bundled. Framework messages such as form and
  validator errors do go through `gettext`, so an entry with the same `msgid` in your own catalog translates them.
- **Per-language template variables** (`LANGUAGE_CODE` via a context processor), language-info tags and filters
  beyond the three listed above.
- **JavaScript catalogs.**

Known caveat: `{% language %}` switches language with the thread-level `activate` and, when the block ends,
re-activates the language that was current before it instead of clearing the thread-level value. On a
multi-threaded server that pins the worker thread to that language for later requests. Until this changes, prefer
rendering the fragment inside `override_language` in the view and passing the result to the template.
