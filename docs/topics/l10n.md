# Localisation

Localisation is the presentation side of internationalisation: date, time and number formats that follow the
active language, and time zones. This page covers `rango::utils::formats`, the bundled locale data, the places the
framework applies it (template filters and forms), the related settings, `rango::utils::timezone`, and what is not
localised yet.

Translating text is covered in [Internationalisation](i18n.md).

## How a format is resolved

```rust
use rango::utils::formats::{get_format, get_format_list, get_format_str};
```

Every lookup goes through `get_format(name, lang)`:

1. Take the language: the `lang` argument, or the [active language](i18n.md#choosing-the-language) when it is
   `None`.
2. Look the name up in the bundled data for that locale: first the full locale (`de-ch` is `de_CH`), then the
   base language (`de`).
3. If the locale data has no value for that name, use the corresponding setting.

The locale data therefore takes precedence over the settings. This matters for the default configuration: the
`en` locale defines every format, so with `language_code = "en-us"` changing `date_format` or
`decimal_separator` in your settings has no visible effect. The settings are the fallback for languages without
bundled data and for the names a locale leaves out. To force a particular format, pass it explicitly where it is
used (a format string to the `date` filter, `input_formats` on a form field).

```rust
use rango::utils::formats::get_format;

// Explicit language.
assert_eq!(get_format("DATE_FORMAT", Some("de")), "j. F Y");
assert_eq!(get_format("DECIMAL_SEPARATOR", Some("de")), ",");
assert_eq!(get_format("FIRST_DAY_OF_WEEK", Some("en-gb")), 1);

// Active language.
let fmt = get_format("SHORT_DATE_FORMAT", None);
```

`get_format` returns a `serde_json::Value` because formats are strings, numbers or lists. Two typed wrappers use
the active language:

| Function | Returns |
|----------|---------|
| `get_format(name: &str, lang: Option<&str>) -> serde_json::Value` | The raw value; `Null` for an unknown name |
| `get_format_str(name: &str) -> String` | A string format such as `DATE_FORMAT` or `DECIMAL_SEPARATOR` |
| `get_format_list(name: &str) -> Vec<String>` | A list such as `DATE_INPUT_FORMATS`; empty if the value is not a list |
| `number_grouping() -> Vec<usize>` | `NUMBER_GROUPING` as a list of group sizes |

## Format names and settings

| Format name | Setting (fallback) | Default of the setting | Kind |
|-------------|--------------------|------------------------|------|
| `DATE_FORMAT` | `date_format` | `"N j, Y"` | output format |
| `DATETIME_FORMAT` | `datetime_format` | `"N j, Y, P"` | output format |
| `TIME_FORMAT` | `time_format` | `"P"` | output format |
| `YEAR_MONTH_FORMAT` | `year_month_format` | `"F Y"` | output format |
| `MONTH_DAY_FORMAT` | `month_day_format` | `"F j"` | output format |
| `SHORT_DATE_FORMAT` | `short_date_format` | `"m/d/Y"` | output format |
| `SHORT_DATETIME_FORMAT` | `short_datetime_format` | `"m/d/Y P"` | output format |
| `FIRST_DAY_OF_WEEK` | `first_day_of_week` | `0` (Sunday; `1` is Monday) | number |
| `DECIMAL_SEPARATOR` | `decimal_separator` | `"."` | string |
| `THOUSAND_SEPARATOR` | `thousand_separator` | `","` | string |
| `NUMBER_GROUPING` | `number_grouping` | `0` (no grouping) | number or list of numbers |
| `DATE_INPUT_FORMATS` | `date_input_formats` | `"%Y-%m-%d"`, `"%m/%d/%Y"`, `"%m/%d/%y"`, `"%b %d %Y"`, ... | list of parse patterns |
| `TIME_INPUT_FORMATS` | `time_input_formats` | `"%H:%M:%S"`, `"%H:%M:%S.%f"`, `"%H:%M"` | list of parse patterns |
| `DATETIME_INPUT_FORMATS` | `datetime_input_formats` | `"%Y-%m-%d %H:%M:%S"`, `"%m/%d/%Y %H:%M"`, ... | list of parse patterns |

Two more settings affect numbers and are not per-locale:

| Setting | Default | Meaning |
|---------|---------|---------|
| `use_thousand_separator` | `false` | Whether `number_format` / `localize_number` insert thousand separators |
| `format_module_path` | `None` | Defined, but not used: custom per-project format definitions are not supported |

Output formats use the template date-format letters (`j` day without leading zero, `F` full month name, `Y`
four-digit year, `H:i` 24-hour time, `P` 12-hour time with a.m./p.m., and so on; see the
[template filter reference](../ref/template-filters.md)). Input formats use `strftime`-style patterns (`%d.%m.%Y`).

### ISO input formats

When an `*_INPUT_FORMATS` value comes from the locale data, the ISO patterns are appended if they are not already
there, so ISO input is accepted in every bundled locale:

| Name | Appended |
|------|----------|
| `DATE_INPUT_FORMATS` | `%Y-%m-%d` |
| `TIME_INPUT_FORMATS` | `%H:%M:%S`, `%H:%M:%S.%f`, `%H:%M` |
| `DATETIME_INPUT_FORMATS` | `%Y-%m-%d %H:%M:%S`, `%Y-%m-%d %H:%M:%S.%f`, `%Y-%m-%d %H:%M`, `%Y-%m-%d` |

```rust
use rango::utils::formats::get_format;

assert_eq!(
    get_format("DATE_INPUT_FORMATS", Some("de")),
    rango::json!(["%d.%m.%Y", "%d.%m.%y", "%Y-%m-%d"]),
);
```

Values that come from the settings are returned unchanged.

## Bundled locales

The data lives in `crates/rango-core/data/locale_formats.json` and is compiled into the binary; nothing is read
from disk at run time. It covers 84 locales:

`ar`, `ar_DZ`, `az`, `bg`, `bn`, `bs`, `ca`, `ckb`, `cs`, `cy`, `da`, `de`, `de_CH`, `el`, `en`, `en_AU`, `en_CA`,
`en_GB`, `en_IE`, `eo`, `es`, `es_AR`, `es_CO`, `es_MX`, `es_NI`, `es_PR`, `et`, `eu`, `fa`, `fi`, `fr`, `fr_BE`,
`fr_CA`, `fr_CH`, `fy`, `ga`, `gd`, `gl`, `he`, `hi`, `hr`, `hu`, `id`, `ig`, `is`, `it`, `ja`, `ka`, `km`, `kn`,
`ko`, `ky`, `lt`, `lv`, `mk`, `ml`, `mn`, `ms`, `nb`, `nl`, `nn`, `pl`, `pt`, `pt_BR`, `ro`, `ru`, `sk`, `sl`, `sq`,
`sr`, `sr_Latn`, `sv`, `ta`, `te`, `tg`, `th`, `tk`, `tr`, `ug`, `uk`, `uz`, `vi`, `zh_Hans`, `zh_Hant`.

Not every locale defines every name. For example `ja` has no `FIRST_DAY_OF_WEEK` or input formats, and `hi` has no
`NUMBER_GROUPING`; those names fall back to the settings. A regional locale falls back to its base language name
by name: `en_GB` is consulted first, then `en` for any name `en_GB` lacks, and only then the settings.

Some examples of what the data contains:

| Locale | `DATE_FORMAT` | `SHORT_DATE_FORMAT` | `TIME_FORMAT` | Decimal | Thousand | First day |
|--------|---------------|---------------------|---------------|---------|----------|-----------|
| `en` | `N j, Y` | `m/d/Y` | `P` | `.` | `,` | 0 |
| `en_GB` | `j M Y` | `d/m/Y` | `P` | `.` | `,` | 1 |
| `de` | `j. F Y` | `d.m.Y` | `H:i` | `,` | `.` | 1 |
| `fr` | `j F Y` | `d/m/Y` | `H:i` | `,` | non-breaking space | 1 |
| `cs` | `j. E Y` | `d.m.Y` | `G:i` | `,` | non-breaking space | 1 |

## Dates and times in templates

The `date` and `time` filters accept either a format string or the name of a format. A named format is resolved
with `get_format` for the active language:

```html
{{ article.published|date }}                      {# DATE_FORMAT #}
{{ article.published|date:"SHORT_DATE_FORMAT" }}
{{ article.published|date:"DATETIME_FORMAT" }}
{{ article.published|date:"YEAR_MONTH_FORMAT" }}
{{ article.published|date:"MONTH_DAY_FORMAT" }}
{{ article.published|date:"D d M Y" }}            {# explicit format, same in every language #}
{{ article.published|time }}                      {# TIME_FORMAT #}
{{ article.published|time:"H:i" }}
```

The names recognised are `DATE_FORMAT`, `DATETIME_FORMAT`, `SHORT_DATE_FORMAT`, `SHORT_DATETIME_FORMAT`,
`TIME_FORMAT`, `YEAR_MONTH_FORMAT` and `MONTH_DAY_FORMAT`. Anything else is treated as a format string.

With `LocaleMiddleware` active, the same template gives:

| Active language | `{{ d\|date }}` | `{{ d\|date:"SHORT_DATE_FORMAT" }}` |
|-----------------|-----------------|--------------------------------------|
| `en-us` | `Jan. 5, 2024` | `01/05/2024` |
| `en-gb` | `5 Jan 2024` | `05/01/2024` |
| `de` | `5. January 2024` | `05.01.2024` |

Note the German row: the *order and punctuation* follow the locale, but month and weekday **names are always
English** (see [Not localised yet](#not-localised-yet)). For fully localised dates today, use numeric formats such
as `SHORT_DATE_FORMAT`.

A date or time printed without a filter (`{{ article.published }}`) uses a fixed format (`N j, Y, P` for
datetimes, `N j, Y` for dates, `P` for times) regardless of the language. Use the filters when output should
follow the locale.

## Dates and times in forms

Date, time and datetime form fields parse input with the active locale's input formats:

| Field | Patterns tried, in order |
|-------|--------------------------|
| `Field::date()` | `DATE_INPUT_FORMATS` |
| `Field::time()` | `TIME_INPUT_FORMATS` |
| `Field::datetime()` | `DATETIME_INPUT_FORMATS`, then `DATE_INPUT_FORMATS` |

So under `de` a date field accepts `24.12.2024`, `24.12.24` and `2024-12-24`; under `en-us` it accepts
`12/24/2024`, `2024-12-24`, `Dec 24 2024` and the other default patterns.

The matching text widgets display an existing value with the **first** pattern of the same list, so a value
round-trips: what the form shows is something the field will parse. The date select widget
(`Widget::select_date`) orders its year, month and day drop-downs according to `DATE_FORMAT`.

To pin a field to specific formats regardless of language, set them on the field:

```rust
use rango::forms::Field;

let birthday = Field::date().input_formats(&["%d.%m.%Y", "%Y-%m-%d"]);
```

Number fields are not localised: decimal and float fields expect `.` as the decimal separator in every language.

## Formatting numbers

```rust
use rango::utils::formats::{localize_number, number_format};
```

`number_format` formats a number given as a decimal string. It is a pure function apart from reading
`use_thousand_separator`:

```rust
pub fn number_format(
    number: &str,              // "-1234567.891"
    decimal_sep: &str,         // ","
    decimal_pos: Option<usize>,// digits after the separator; None keeps the input's
    grouping: &[usize],        // [3], or [3, 2, 0]
    thousand_sep: &str,        // "."
    force_grouping: bool,      // group even when use_thousand_separator is false
) -> String
```

```rust
use rango::utils::formats::number_format;

assert_eq!(number_format("1234567.891", ",", Some(2), &[3], ".", true), "1.234.567,89");
assert_eq!(number_format("1234.5", ".", Some(2), &[3], ",", true), "1,234.50");
assert_eq!(number_format("1234567", ".", None, &[3, 2, 0], ",", true), "12,34,567");
```

Details:

- `decimal_pos` pads with zeros or **truncates**; it does not round. Round the value before formatting.
- Grouping sizes apply from the right. The last size repeats; a `0` stops grouping, so `[3, 2, 0]` gives one group
  of three, one group of two, and the rest ungrouped.
- Grouping happens only if `force_grouping` is `true` or the `use_thousand_separator` setting is on, **and** the
  first group size is greater than zero **and** the separator is not empty.
- A value that is zero after truncation loses its minus sign.

`localize_number(number, decimal_pos)` is `number_format` with the active language's `DECIMAL_SEPARATOR`,
`NUMBER_GROUPING` and `THOUSAND_SEPARATOR`, and without forcing grouping:

```rust
use rango::utils::formats::localize_number;
use rango::utils::translation::override_language;

let price = override_language("de", async { localize_number("1234.50", Some(2)) }).await;
// "1234,50" by default, "1.234,50" with use_thousand_separator = true
```

Rango does not apply this automatically when a number is printed in a template. Format the number in the view and
pass the string to the template.

## Time zones

```rust
use rango::utils::timezone::{self, Tz};
```

### Settings

| Setting | Default | Meaning |
|---------|---------|---------|
| `use_tz` | `true` | Datetimes are time-zone aware and stored in UTC |
| `time_zone` | `"America/Chicago"` (the project template sets `"UTC"`) | The default time zone, an IANA name such as `"Europe/Prague"` |

With `use_tz = true`:

- datetime model fields are `DateTime<Utc>`; values read from the database are UTC;
- datetime form fields interpret what the user typed in the *current time zone* and convert it to UTC, and show
  initial values converted to the current time zone;
- generic views and `rango::views::generic::model_value` hand datetimes to templates converted to the current time
  zone;
- the `{% now %}` tag prints the current time in the current time zone.

With `use_tz = false` datetimes are naive (`NaiveDateTime`) throughout and no conversion takes place.

Rust's types already separate aware (`DateTime<Tz>`) from naive (`NaiveDateTime`) values, so there are no
"is this aware?" helpers; the compiler tells you. Rango never changes the process's `TZ` environment variable.

### The default and the current time zone

The *default* time zone is the `time_zone` setting. The *current* time zone is the one in effect for the running
task: the innermost `override_tz` scope, or the default when there is none.

| Function | Meaning |
|----------|---------|
| `get_default_timezone() -> Result<Tz>` | `time_zone` parsed; an `ImproperlyConfigured` error for an unknown name |
| `get_current_timezone() -> Result<Tz>` | The innermost override, else the default |
| `override_tz(tz: Tz, fut) -> F::Output` (async) | Run a future with `tz` as the current time zone |
| `override_tz_sync(tz: Tz, body) -> R` | The same for a synchronous closure |
| `get_fixed_timezone(offset_minutes: i32) -> Option<FixedOffset>` | A fixed UTC offset |

Like the active language, the override is task-local: tasks started with `tokio::spawn` inside it do not inherit
it.

There is no middleware that selects a time zone per request. If users have their own time zone, wrap the work in
`override_tz` yourself:

```rust
use rango::http::{HttpRequest, HttpResponse};
use rango::utils::timezone::{self, Tz};
use rango::Result;

async fn dashboard(req: HttpRequest) -> Result<HttpResponse> {
    let tz: Tz = req
        .cookies()
        .get("tz")
        .and_then(|name| name.parse().ok())
        .unwrap_or(timezone::get_default_timezone()?);
    timezone::override_tz(tz, async move {
        let local = timezone::localtime(timezone::now(), None)?;
        Ok(HttpResponse::new(format!("It is {}", local.format("%H:%M"))))
    })
    .await
}
```

### Working with datetimes

| Function | Meaning |
|----------|---------|
| `now() -> DateTime<Utc>` | The current time, always aware and in UTC |
| `now_naive() -> Result<NaiveDateTime>` | The current wall-clock time in the default time zone, for `use_tz = false` projects |
| `localtime(value: DateTime<Utc>, tz: Option<Tz>) -> Result<DateTime<Tz>>` | Convert to `tz`, or to the current time zone when `None` |
| `make_aware(value: NaiveDateTime, tz: Tz) -> DateTime<Tz>` | Attach a time zone to a wall-clock time |
| `make_naive(value: &DateTime<Z>, tz: Tz) -> NaiveDateTime` | The wall-clock time of `value` in `tz` |

```rust
use rango::db::chrono::{NaiveDate, Utc};
use rango::utils::timezone::{localtime, make_aware, make_naive, now, Tz};

let prague: Tz = "Europe/Prague".parse().unwrap();

// A wall-clock time entered by a user in Prague, stored as UTC.
let naive = NaiveDate::from_ymd_opt(2024, 7, 1).unwrap().and_hms_opt(9, 30, 0).unwrap();
let stored = make_aware(naive, prague).with_timezone(&Utc);   // 07:30 UTC

// And back for display.
let shown = localtime(stored, Some(prague))?;                  // 09:30 +02:00
assert_eq!(make_naive(&stored, prague), naive);

let created = now();                                           // DateTime<Utc>
```

`make_aware` never fails. Around daylight-saving changes it picks a definite answer:

- an **ambiguous** time (the hour that occurs twice when clocks go back) resolves to the first occurrence;
- a **non-existent** time (the hour skipped when clocks go forward) is interpreted with the offset that was in
  force before the gap.

Form fields are stricter: a datetime field rejects an ambiguous or non-existent local time with the validation
error code `ambiguous_timezone`, because guessing would silently store the wrong instant.

### Time zones in templates

A `DateTime<Utc>` that you put into a template context yourself is rendered in UTC. Convert it first if it should
appear in the current time zone, or pass model instances through `rango::views::generic::model_value`, which
converts datetime fields for you.

The `rango.template.context_processors.tz` context processor adds a `TIME_ZONE` variable holding the `time_zone`
setting (the default zone, not the current override).

### Time zones in queries

Datetime parts extracted in the database (`__date`, `__time`, `__month`, `__day`, `__hour`, ...) are computed in
UTC, not in the current time zone. Keep that in mind for "everything published today" style filters on a site
whose users are far from UTC; computing the UTC bounds of the local day in Rust and filtering with a range is
exact:

```rust
use rango::db::chrono::{NaiveDate, Utc};
use rango::utils::timezone::{get_current_timezone, make_aware};

let tz = get_current_timezone()?;
let day = NaiveDate::from_ymd_opt(2024, 7, 1).unwrap();
let start = make_aware(day.and_hms_opt(0, 0, 0).unwrap(), tz).with_timezone(&Utc);
let end = make_aware(day.succ_opt().unwrap().and_hms_opt(0, 0, 0).unwrap(), tz).with_timezone(&Utc);
// filter pub_date >= start and pub_date < end
```

## Not localised yet

- **Month and weekday names** produced by the `date` filter and `{% now %}` are English in every language. The
  letters `F`, `M`, `N`, `E`, `b`, `l` and `D` do not consult the message catalogs.
- **Numbers in templates.** Printing a number does not apply the locale's separators, and `floatformat` and
  `intcomma` always use `.` and `,`. Use `localize_number` in the view.
- **`localize` / `unlocalize`** template filters and a `{% localize %}` block do not exist.
- **Number input in forms.** Decimal and float fields do not accept a localised decimal separator.
- **Dates printed without a filter** use a fixed English format.
- **Custom format definitions** per project (`format_module_path`) are not read. A bundled locale's formats cannot
  be overridden from settings; pass explicit formats instead.
- **Per-request time zone selection** has no middleware, and there is no template tag library for time zone
  conversion.
- **`timesince` / `timeuntil`** output is English.
