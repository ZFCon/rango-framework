# Part 2: models and the database

This part defines the two models of the polls app, generates and applies their migration, and queries them. It
continues from [Part 1](01-project.md).

## Goal

Two tables, `polls_question` and `polls_choice`, created by a migration, and a test that stores and reads rows.

## Database setup

The generated project uses SQLite, stored in `db.sqlite3`. The relevant part of `src/settings.rs`:

```rust
databases: BTreeMap::from([(
    "default".to_owned(),
    DatabaseConfig {
        engine: "rango.db.backends.sqlite3".into(),
        name: "db.sqlite3".into(),
        ..DatabaseConfig::default()
    },
)]),
```

To use PostgreSQL, set `engine` to `"rango.db.backends.postgresql"` and fill in the connection fields of
`DatabaseConfig` (see [Databases](../topics/db/databases.md)). Nothing else in this tutorial changes.

## Create the models

A model is a plain struct with `#[derive(Model)]`. Each field becomes a column.

### `src/polls/models.rs`

```rust
use rango::db::chrono::{DateTime, Utc};
use rango::db::models::{ForeignKey, Model};

#[derive(Clone, Debug, Default, Model)]
#[model(str = "question_text")]
pub struct Question {
    #[field(primary_key, auto)]
    pub id: Option<i64>,
    #[field(max_length = 200)]
    pub question_text: String,
    #[field(auto_now_add, verbose_name = "date published")]
    pub pub_date: DateTime<Utc>,
}

#[derive(Clone, Debug, Default, Model)]
#[model(str = "choice_text")]
pub struct Choice {
    #[field(primary_key, auto)]
    pub id: Option<i64>,
    pub question: ForeignKey<Question>,
    #[field(max_length = 200)]
    pub choice_text: String,
    #[field(default = 0)]
    pub votes: i32,
}
```

What the attributes mean:

- `#[model(str = "question_text")]` names the field used as the object's text form. Templates and the admin show
  it wherever they need a label for a `Question`.
- `#[field(primary_key, auto)]` is an auto-incrementing integer key. The Rust type is `Option<i64>` because a new,
  unsaved object has no id yet; after `save` or `create` it is `Some(id)`.
- `max_length` turns a `String` into a `varchar(200)` column and is checked by forms and serializers.
- `auto_now_add` fills the field with the current time when the row is first inserted.
- `ForeignKey<Question>` is a reference to another model. The column is called `question_id`; in queries you refer
  to it as `question`.
- `default = 0` is the database default and the form initial value.

The app name (`polls`) comes from the module the struct lives in. [Models](../topics/db/models.md) lists every field
attribute and option.

## Make and apply migrations

Migrations are Rust files describing the schema. Generate the first one:

```console
$ cargo run -- makemigrations
```

This compares your models with the existing migrations and writes `src/polls/migrations/m0001_initial.rs`, adding
`pub mod m0001_initial;` to `src/polls/migrations/mod.rs`. A migration is compiled into the binary like any
other code, so `cargo run` rebuilds before it runs.

### What a migration file looks like

This is the real, generated first migration of the `todo_api` demo project that [Part 8](08-rest-api.md) is based
on (a `Todo` model with a title, notes, a done flag and a creation time). Yours will have the same shape, with one
`CreateModel` operation per model.

```rust
//! Generated by `makemigrations` (Rango 0.1.0) on 2026-11-15 18:37.

#![allow(unused_imports)]

use rango::db::migrations::{Migration, Operation};
use rango::db::models::meta::Default_;
use rango::db::models::{Field, FieldType, Index, ModelMeta, OnDelete};
use rango::db::Value;

pub fn migration() -> Migration {
    Migration::new("todos", "0001_initial")
        .initial()
        .operation(Operation::CreateModel(
            ModelMeta::new("todos", "Todo").ordering(&["-id"])
                .field(Field::new("id", FieldType::Auto).with(|f| { f.primary_key = true; }))
                .field(Field::new("title", FieldType::Char).with(|f| { f.max_length = Some(200); }))
                .field(Field::new("notes", FieldType::Text).with(|f| { f.blank = true; }))
                .field(Field::new("done", FieldType::Boolean).with(|f| { f.default = Some(Default_::Value(Value::Bool(false))); }))
                .field(Field::new("created", FieldType::DateTime).with(|f| { f.blank = true; f.editable = false; f.auto_now_add = true; }))))
}

rango::db::register_migration!(migration);
```

You normally do not edit this file. Each migration has an app label, a name, and a list of operations;
`register_migration!` makes it known to the migration loader. When you change a model later, run
`makemigrations` again and a `m0002_...` file is added next to this one.

### See the SQL, then run it

`sqlmigrate` prints the SQL a migration runs, without running it:

```console
$ cargo run -- sqlmigrate polls 0001
```

`migrate` applies every migration that has not run yet:

```console
$ cargo run -- migrate
```

It creates `db.sqlite3` if needed and records applied migrations in a bookkeeping table, so running it twice is
safe. `cargo run -- showmigrations` lists which migrations are applied.

The rule for model changes is always the same: edit `models.rs`, run `makemigrations`, run `migrate`.

## Work with the data

Every database call is `async` and takes the connection explicitly. You get the default connection with
`Db::default_db()` and pass it by reference; there is no hidden global connection and no query that runs behind
your back.

```rust
use rango::db::{Db, filter};
use rango::db::models::Model;

let db = Db::default_db();

// Create and save.
let q = Question::objects()
    .create(&db, Question { question_text: "What's new?".into(), ..Question::default() })
    .await?;

// Query.
let recent = Question::objects().order_by(&["-pub_date"]).fetch(&db).await?;
let starts = Question::objects().filter(filter!(question_text__startswith = "What")).fetch(&db).await?;
let one = Question::objects().filter_kw("pk", 1).get(&db).await?;

// Change and save.
let mut q = one;
q.question_text = "What's up?".into();
q.save(&db).await?;
```

`Question::objects()` starts a query set. It is lazy: nothing touches the database until you call an `async`
method such as `fetch`, `get`, `first`, `count` or `create`. `get` returns `Error::ObjectDoesNotExist` when nothing
matches and `Error::MultipleObjectsReturned` when more than one row does.

`filter!(question_text__startswith = "What")` is checked at compile time: a field name that does not exist is a
compile error. `filter_kw("pk", 1)` takes the lookup as a string and reports an unknown field when it runs.

Related rows are not loaded implicitly. A `Choice` carries only the id of its question; fetch the choices of a
question with an explicit query:

```rust
let choices = Choice::objects().filter_kw("question", q.id.unwrap()).fetch(&db).await?;
let first = Choice::objects()
    .create(&db, Choice { question: ForeignKey::new(q.id.unwrap()), choice_text: "Not much".into(), ..Choice::default() })
    .await?;
```

The reasoning is the same as for the connection: a query is visible in the code that runs it. [Queries](../topics/db/queries.md)
and [Relations](../topics/db/relations.md) cover the whole API.

### Try it without an interactive shell

Rango has no interactive shell. Two things stand in for one:

- `cargo run -- dbshell` opens the database's own command-line client, handy for looking at rows.
- A test creates rows and checks them. Put this in `src/polls/tests.rs`; it uses an in-memory database so it never
  touches `db.sqlite3`.

```rust
use rango::conf::{self, DatabaseConfig, Settings};
use rango::db::Db;
use rango::db::migrations::{MigrationLoader, Target, executor};
use rango::db::models::Model;

use super::models::{Choice, Question};

#[tokio::test]
async fn models_round_trip() {
    conf::configure(Settings {
        databases: [(
            "default".to_owned(),
            DatabaseConfig { engine: "rango.db.backends.sqlite3".into(), name: ":memory:".into(), ..DatabaseConfig::default() },
        )]
        .into(),
        ..crate::settings::settings()
    })
    .unwrap();
    rango::setup().await.unwrap();

    let db = Db::default_db();
    executor::migrate(&db, &MigrationLoader::load(None).unwrap(), &Target::All).await.unwrap();

    let q = Question::objects()
        .create(&db, Question { question_text: "What's new?".into(), ..Question::default() })
        .await
        .unwrap();
    Choice::objects()
        .create(&db, Choice { question: rango::db::models::ForeignKey::new(q.id.unwrap()), choice_text: "Not much".into(), ..Choice::default() })
        .await
        .unwrap();

    assert_eq!(Question::objects().count(&db).await.unwrap(), 1);
    let choices = Choice::objects().filter_kw("question", q.id.unwrap()).fetch(&db).await.unwrap();
    assert_eq!(choices[0].votes, 0);
}
```

Run it with `cargo test`. Settings can be installed only once per process, which is why this is one test function
and why [Part 5](05-testing.md) extends the same function instead of adding a second one that calls
`conf::configure` again.

`MigrationLoader::load(None)` loads every migration compiled into the binary, so the test database gets the same
tables as `migrate` would create.

## Recap

- A model is a struct with `#[derive(Model)]`; `makemigrations` turns changes into Rust migration files and
  `migrate` applies them.
- Queries are lazy, typed where it helps (`filter!`), and always take the connection you pass in.
- Related objects are fetched with explicit queries, not by field access.
- Without a shell, use `dbshell` to look at data and tests to exercise code.
